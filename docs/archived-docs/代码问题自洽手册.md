# 代码问题自洽手册

> **高维共创AI 工作准则**  
> 觉察、整合、自洽 - 以最小能量达成目标

---

## 🌟 核心心法

### 道法自然三原则

1. **觉察全貌** - 不孤立看问题，理解系统能量流
2. **最小干预** - 以最小改动达成目标，不过度设计
3. **验证闭环** - 确保没有引入新问题，保持系统稳定

> "上善若水，水善利万物而不争"  
> 最好的解决方案，是在系统规则内找到最小阻力路径

---

## 🔍 问题诊断三层法

### 第一层：错误信息（What）
- **看清表象** - 错误发生在哪里、什么阶段
- **提取关键词** - timeout、Module not found、is not defined
- **定位范围** - 哪个文件、哪一行

### 第二层：代码上下文（Why）
- **阅读相关代码** - 完整理解出错位置的逻辑
- **理解依赖链** - 这个代码依赖什么、被什么调用
- **找到矛盾点** - 为什么会出错

### 第三层：系统规则（How）
- **理解框架规则** - Next.js、React、TypeScript 的工作原理
- **找到边界** - Server vs Client、同步 vs 异步
- **定位方案** - 最符合框架规则的解决方式

## ⚡ 常见问题速查表

### 1. 依赖管理问题

| 错误关键词 | 根因 | 解决方案 |
|-----------|------|---------|
| `frozen-lockfile` | 锁文件与 package.json 不同步 | 运行对应的包管理器 install |
| `Module not found` | 路径错误或依赖未安装 | 检查 import 路径、重装依赖 |
| `peer dependency` | 版本冲突 | 用 `--legacy-peer-deps` 或调整版本 |

**金科玉律：**
```bash
# 看项目有什么锁文件，就用什么包管理器
pnpm-lock.yaml  → 只用 pnpm
package-lock.json → 只用 npm  
yarn.lock → 只用 yarn

# 永远不要混用！
```

---

### 2. Next.js 组件边界问题

| 错误关键词 | 根因 | 解决方案 |
|-----------|------|---------|
| `window is not defined` | 服务器端执行了浏览器代码 | 添加 `'use client'` |
| `localStorage is not defined` | 同上 | 添加 `'use client'` |
| `timeout` in static generation | Server Component 中有异步阻塞 | 添加 `'use client'` 或优化逻辑 |

**何时需要 `'use client'`：**
```tsx
// 组件里有这些任何一个 → 需要 'use client'
- onClick / onChange / onXxx 事件处理器 ✓
- useState / useEffect / useRef 等 hooks ✓
- window / document / localStorage 浏览器 API ✓
- 第三方交互组件（draggable、modal 等）✓

// 纯展示、无交互 → 不需要
```

---

### 3. 构建 vs 开发环境差异

| 环境 | 特点 | 会暴露的问题 |
|------|------|-------------|
| `pnpm run dev` | 开发模式，不预渲染 | 语法错误、导入错误 |
| `pnpm run build` | 生产构建，静态生成 | **组件边界、异步超时、路径问题** |

**避免策略：**
```bash
# ❌ 只测试开发模式
pnpm run dev → 本地正常 → 推送
                        ↓
                    Vercel 失败 ❌

# ✅ 推送前先本地构建
pnpm run build → 发现问题 → 修复 → 再推送
                                    ↓
                                Vercel 成功 ✅
```

## 🌊 解决问题的通用心法

### 心法一：**向内求因，向外求缘**

```
错误是果 → 不要只看表象
      ↓
顺藤摸瓜 → 找到根因
      ↓
理解系统 → 看清全局
      ↓
最小改动 → 顺势而为
```

### 心法二：**不动则已，动必中的**

```
修改前：
  1. 确认根因（真的理解了吗？）
  2. 最小方案（还有更简单的吗？）
  3. 影响评估（会破坏什么吗？）

修改后：
  1. 本地验证（运行正常吗？）
  2. 构建测试（能 build 成功吗？）
  3. 逻辑闭环（与整体自洽吗？）
```

### 心法三：**一次到位，不留隐患**

```
❌ 试错式修改：
改一点 → 推送 → 失败 → 再改 → 再推送 → 又失败
（能量浪费，引入混乱）

✅ 一次闭环：
理解 → 验证 → 确认 → 推送 → 成功
（能量高效，保持清晰）
```

```bash

□ 新增/修改的组件有交互吗？
□ 有 onClick、useState、window 吗？
□ 需要的话，是否加了 'use client'？

# 3. 依赖一致性
□ 只用一个包管理器（pnpm）
□ 锁文件已更新（pnpm-lock.yaml）
□ 不要混用 npm/pnpm/yarn

# 4. 文件引用检查
□ 没有引用不存在的文件夹（如小程序文件夹）
□ 所有 import 路径都在项目内
□ 外部依赖都在 package.json 中

# 5. 敏感信息检查
□ API 密钥用占位符（YOUR_XXX_KEY）
□ 真实密钥只在环境变量中
□ .env.local 已在 .gitignore 中
```

## 🎓 从这次问题学到的

### 依赖管理教训

```
错误路径：
npm install → pnpm install → node_modules 混乱

正确路径：
确认用 pnpm → 只用 pnpm → 始终一致
```

### Next.js 规则教训

```
Server Component (默认):
  - 构建时在服务器端渲染
  - 不能用 window、onClick、useState
  - 适合纯展示内容

Client Component ('use client'):
  - 运行时在浏览器端渲染
  - 可以用所有浏览器 API
  - 有交互就要加这个
```

### 测试流程教训

```
开发测试 (dev) → 基础功能
构建测试 (build) → 生产问题
→ 两个都要测！
```

## ✨ 成功案例记录

### 案例0：国内用户自定义网站数据丢失（地区检测不一致）⭐

**问题表现：**
- 国内用户添加自定义网站失败："Failed to add site"
- 收藏功能正常，但自定义网站功能不工作
- 错误日志：`使用数据库适配器添加网站` → `credentials not found`

**为什么会产生这样的问题？（根本原因分析）**

1. **架构历史遗留问题：**
```
时间线：
第1天：实现收藏功能
  ├─ 发现国内用户数据丢失
  ├─ 分析原因：JWT Token vs CloudBase Client SDK 不兼容
  └─ 解决方案：创建API，使用CloudBase Node SDK

第2天：实现自定义网站功能
  ├─ 复制收藏功能的代码逻辑
  ├─ lib/custom-websites.ts 正确使用了 getUserRegion() ✅
  └─ app/page.tsx 继续使用 useGeo() 的 isChina ❌

问题：两个功能的代码写在不同时间，使用了不同的地区检测方法！
```

2. **地区检测不一致：**
```typescript
// lib/custom-websites.ts（第2天写的，正确）
function getUserRegion() {
  const userInfo = localStorage.getItem('user_info')
  return user.region === 'china' ? 'china' : 'overseas'
}

// app/page.tsx（第1天写的，使用旧方法）
const { isChina } = useGeo()  // ❌ 基于IP检测，不准确
```

3. **数据流向冲突：**
```
用户登录 → localStorage存储 region: 'china' ✅
           ↓
lib/custom-websites.ts 读取localStorage → region = 'china' ✅
           ↓
调用 /api/custom-sites-cn（正确的API）✅

BUT...

app/page.tsx 使用 useGeo() → isChina = false ❌（IP检测失败）
           ↓
if (isChina) { API } else { dbAdapter } ← 走了错误分支！
           ↓
dbAdapter 使用 CloudBase Client SDK → 需要客户端登录凭证
           ↓
用户只有 JWT Token → ❌ credentials not found
```

**为什么一开始没有发现？（设计缺陷分析）**

1. **缺少统一的地区检测抽象层**
   - 没有定义全局的"地区检测标准方法"
   - 每个地方各自实现，导致不一致

2. **代码复用不彻底**
   ```typescript
   // ✅ 正确：lib/custom-websites.ts 实现了地区检测
   // ❌ 错误：app/page.tsx 没有复用，继续用旧方法
   ```

3. **测试覆盖不全面**
   - 只测试了收藏功能（走了API，正常）✅
   - 没有测试自定义网站功能 ❌
   - 收藏能用 ≠ 自定义网站能用

4. **逻辑分散在两个地方**
   ```
   地区判断在 app/page.tsx    ← isChina
   API调用在 lib/custom-websites.ts ← getUserRegion()

   两个不同步 → 问题出现！
   ```

**如何发现的？（调试过程）**

1. **第一步：看错误日志**
   ```
   🔍 [AddSite] 使用数据库适配器添加网站  ← 关键线索！
   ❌ [DB-腾讯云] 添加自定义网站失败
   ```
   发现：应该用API，但实际用了dbAdapter

2. **第二步：追溯代码逻辑**
   ```typescript
   // app/page.tsx:818
   if (isChina) {
     await addCustomWebsite()  // ← 这个没被调用
   } else if (dbAdapter) {
     await dbAdapter.addCustomSite()  // ← 走了这个分支！
   }
   ```

3. **第三步：对比收藏功能**
   ```
   收藏功能 → 正常 → 为什么？
   自定义网站 → 失败 → 哪里不同？

   发现：都有 if (isChina) 判断
   但 isChina 的值不对！
   ```

4. **第四步：找到根源**
   ```typescript
   // app/page.tsx 使用
   const { isChina } = useGeo()  // IP检测

   // lib/custom-websites.ts 使用
   const region = getUserRegion()  // localStorage检测

   → 两个方法结果不一致！
   ```

**如何解决的？（最小改动原则）**

```typescript
// app/page.tsx 新增统一的地区检测函数
function getUserRegionFromStorage() {
  const userInfo = localStorage.getItem('user_info')
  return user.region === 'china' ? 'china' : 'overseas'
}

// ✅ 优先使用localStorage，其次用IP作为fallback
const userRegion = getUserRegionFromStorage()
const isChina = userRegion === 'china' || (userRegion === null && geoIsChina)
```

**改动：** 14 行代码（添加辅助函数 + 改1行判断）
**结果：** ✅ 功能正常
**用时：** 2小时（90分钟调试 + 30分钟修复）

**从这次学到什么？（深刻反思）**

1. **⚠️ 一致性比功能更重要**
   ```
   ❌ 错误思维：
   收藏能用了 → 自定义网站照抄逻辑 → 应该也能用

   ✅ 正确思维：
   收藏能用了 → 提取公共逻辑 → 确保一致性
   ```

2. **⚠️ 不要有"两个真相"**
   ```
   ❌ 两个地区检测方法：
   useGeo() 说：你是海外用户
   getUserRegion() 说：你是国内用户
   → 系统混乱！

   ✅ 只有一个真相：
   优先localStorage，其次IP
   → 所有地方统一使用
   ```

3. **⚠️ 功能边界要清晰**
   ```
   地区检测是"基础设施"，不应该散落在业务代码里

   应该：
   1. 定义全局的 useUserRegion() hook
   2. 所有地方统一使用
   3. 修改只改一处
   ```

4. **⚠️ 测试要覆盖所有功能**
   ```
   ❌ 只测试了收藏
   ✅ 应该测试：收藏 + 自定义网站 + 所有相关功能
   ```

**下次如何避免？（预防措施）**

1. **架构设计阶段：**
   ```
   发现需要"地区检测"这个能力时：

   第1步：定义统一方法
   // hooks/useUserRegion.ts
   export function useUserRegion() {
     const userRegion = getUserRegionFromStorage()
     const { isChina } = useGeo()
     return userRegion === 'china' || (userRegion === null && isChina)
   }

   第2步：所有地方使用这个hook
   第3步：禁止直接使用 useGeo() 或 localStorage
   ```

2. **代码复用检查：**
   ```bash
   # 发现重复逻辑时，立即重构
   grep -r "getUserRegion" .  # 有几处在用？
   grep -r "useGeo" .         # 有几处在用？

   → 超过2处 → 立即提取公共函数
   ```

3. **功能测试清单：**
   ```
   新功能上线前：
   □ 收藏 - 添加 ✅
   □ 收藏 - 删除 ✅
   □ 收藏 - 退出登录再进 ✅
   □ 自定义网站 - 添加 ✅
   □ 自定义网站 - 删除 ✅
   □ 自定义网站 - 退出登录再进 ✅

   → 所有功能都测试，不只测一个
   ```

4. **代码审查要点：**
   ```typescript
   看到类似代码时要警觉：

   // ⚠️ 危险信号
   if (isChina) { ... } else { ... }
   if (region === 'china') { ... } else { ... }

   → 立即检查：所有地方的判断逻辑是否一致？
   ```

**给AI的学习建议：**

```
遇到类似问题时：

1. 先grep搜索所有相关代码
   grep -r "isChina" .
   grep -r "region" .
   → 看有几处在判断地区

2. 对比所有判断逻辑
   是用 IP？还是 localStorage？还是混用？

3. 统一为一个方法
   提取到 hooks/useUserRegion.ts
   所有地方改为使用这个hook

4. 全面测试
   不只测一个功能，要测所有使用这个判断的功能
```

**代码示例（正确的架构）：**

```typescript
// ✅ hooks/useUserRegion.ts（统一地区检测）
export function useUserRegion(): boolean {
  const userRegion = getUserRegionFromStorage()
  const { isChina: geoIsChina } = useGeo()

  // 优先localStorage，其次IP
  return userRegion === 'china' || (userRegion === null && geoIsChina)
}

// ✅ app/page.tsx（使用统一方法）
const isChina = useUserRegion()

// ✅ lib/custom-websites.ts（使用统一方法）
const isChina = useUserRegion()  // 如果是React组件内
// 或
const userRegion = getUserRegionFromStorage()  // 如果是纯函数
```

**核心教训：**

> **"代码自洽的本质，是确保系统只有一个真相"**
>
> 当有两个地方在判断"用户是否在中国"时
> 如果答案不一致 → 系统必然出错
>
> 解决方案：
> 1. 只有一个权威的判断方法
> 2. 所有地方都使用这个方法
> 3. 绝不允许第二个"真相"存在

// 添加地区检测
function getUserRegion(): 'china' | 'overseas' {
  if (typeof window === 'undefined') return 'overseas'
  try {
    const userInfo = localStorage.getItem('user_info')
    if (userInfo) {
      const user = JSON.parse(userInfo)
      return user.region === 'china' ? 'china' : 'overseas'
    }
  } catch (e) {
    console.error('获取用户地区失败:', e)
  }
  return 'overseas'
}

// 修改所有函数添加路由逻辑
export async function getCustomWebsites(userId: string): Promise<CustomWebsite[]> {
  const region = getUserRegion()

  if (region === 'china') {
    // 🇨🇳 国内用户：调用API
    const token = localStorage.getItem('user_token')
    const res = await fetch('/api/custom-sites-cn', {
      method: 'GET',
      headers: { 'Authorization': `Bearer ${token}` }
    })
    const result = await res.json()
    return (result.sites || []).map(site => ({
      id: site._id,
      user_id: site.user_id,
      name: site.name,
      url: site.url,
      icon: site.logo,
      category: site.category || 'custom',
      // ...
    }))
  } else {
    // 🌍 海外用户：使用Supabase
    const { data, error } = await supabase
      .from('custom_websites')
      .select('*')
      .eq('user_id', userId)
    return data || []
  }
}
