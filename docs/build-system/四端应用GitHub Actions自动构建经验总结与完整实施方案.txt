【1.1 我们遇到的主要问题】

问题1：Android Gradle 构建失败
├─ 现象：chmod: cannot access 'gradlew': No such file or directory
├─ 根本原因：缺少完整的 Gradle Wrapper 基础设施
└─ 错误根源：假设项目已经有 gradlew，实际上是空项目

问题2：Android 仓库配置冲突
├─ 现象：Build was configured to prefer settings repositories over project repositories
├─ 根本原因：Gradle 7+ 使用 FAIL_ON_PROJECT_REPOS 模式，不允许在 build.gradle 中定义仓库
└─ 错误根源：使用了过时的 Gradle 配置模式

问题3：Android 缺少应用图标
├─ 现象：AndroidManifest.xml 引用 @mipmap/ic_launcher 但文件不存在
├─ 根本原因：TWA 项目缺少完整的 mipmap 资源目录
└─ 错误根源：没有生成所有 Android 密度的图标文件

问题4：Tauri 配置结构不正确（反复失败）
├─ 现象：多次尝试修改 tauri.conf.json 都失败
│  ├─ 尝试1：identifier 位置错误
│  ├─ 尝试2：frontendDist: false 不支持
│  ├─ 尝试3：删除 build 对象后 feature 不存在
│  └─ 尝试4：tauri-plugin-log 版本格式错误
├─ 根本原因：**不断猜测配置，而不是使用官方生成工具**
└─ 错误根源：试图手动编写复杂的配置文件，而不是从官方模板开始

问题5：Tauri 强制要求 frontendDist 有效（终局问题）
├─ 现象：所有绕过 frontendDist 验证的尝试都失败
│  ├─ 尝试 frontendDist: false → 不支持
│  ├─ 尝试删除 build 对象 → 配置无效
│  └─ 尝试指向不存在的目录 → 构建时验证失败
├─ 根本原因：**Tauri v2.9.1 硬性要求 frontendDist 必须包含有效的 index.html**
└─ 错误根源：试图绕过框架的基本要求，而不是满足它

问题6：删除依赖但忘记删除代码
├─ 现象：Cargo.toml 删除了 tauri-plugin-log，但 src/lib.rs 还在使用
├─ 根本原因：修改不完整，只改了依赖声明，没改使用代码
└─ 错误根源：没有全局搜索依赖的所有使用位置

问题7：Tauri capabilities 配置错误
├─ 现象：capability with identifier shell-open not found
├─ 根本原因：Tauri v2 的 capabilities 系统不是简单的字符串数组
└─ 错误根源：使用了不存在的内置 capability 名称


【1.2 核心教训总结】

🔴 教训1：不要猜测复杂系统的配置
✅ 正确做法：使用官方 CLI 工具生成标准模板
    - Tauri: npx tauri init --ci
    - Android: 使用 Android Studio 创建项目
    - iOS: npx cap add ios

🔴 教训2：当多次尝试都失败时，要"推倒重建"
✅ 正确做法：
    1. 停止修补式修复
    2. 删除所有手动配置的文件
    3. 使用官方工具重新生成
    4. 只做最小化的必要修改

🔴 教训3：不要试图绕过框架的核心要求
✅ 正确做法：
    - 理解框架的设计哲学
    - 满足框架的要求，而不是绕过它
    - 例如：Tauri 要 index.html → 就创建一个最小的 index.html

🔴 教训4：修改依赖时要全局搜索使用位置
✅ 正确做法：
    1. 删除依赖前，先搜索所有使用该依赖的代码
    2. 使用 grep 或 IDE 全局搜索
    3. 确保代码和依赖声明同步修改

🔴 教训5：错误信息要"直达根源"
✅ 正确做法：
    - "chmod: cannot access 'gradlew'" → 不是权限问题，是文件缺失
    - "frontendDist validation failed" → 不是路径问题，是必须要 index.html
    - 不要被表面错误信息误导，要理解根本原因


【1.3 问题解决的关键转折点】

❌ 前期（反复失败）：
    - 手动编写配置文件
    - 不断修补错误
    - 试图绕过框架限制
    - 每次只解决表面问题

✅ 转折点（用户提出"推倒重建"）：
    "我们必须停止猜测，重新生成一个全新的、干净的 Tauri 项目模板"
    → 使用 npx tauri init --ci 重新生成
    → 立即得到正确的基础配置

✅ 终局方案（回归 Web 原理）：
    - 问题：Tauri 必须要 index.html
    - 方案：创建最小化的 index.html，用 <meta refresh> 重定向
    - 效果：满足框架要求，又实现了加载远程网站的目标
    - 关键：**不绕过要求，而是巧妙地满足要求**

【2.1 面对新框架/工具时的标准流程】

步骤1：使用官方 CLI 生成标准项目
    ├─ 不要手动创建配置文件
    ├─ 不要从网上复制粘贴旧版本配置
    └─ 使用最新版本的 CLI 工具

步骤2：先让"Hello World"跑起来
    ├─ 不要急于实现复杂功能
    ├─ 先验证基础配置是否正确
    └─ 本地构建成功后再配置 CI/CD

步骤3：做最小化修改
    ├─ 每次只改一个配置项
    ├─ 立即测试验证
    └─ 记录每次修改的目的和效果

步骤4：遇到错误时的正确响应
    ├─ 不要立即"修补"
    ├─ 先理解错误的根本原因
    ├─ 搜索官方文档和 GitHub Issues
    └─ 如果多次失败，考虑重新生成项目


【2.2 CI/CD 构建失败的标准排查流程】

第一步：分离问题（本地 vs CI）
    问：这个问题在本地能复现吗？
    ├─ 能复现 → 是配置问题，与 CI 无关
    └─ 不能复现 → 是 CI 环境问题

第二步：查看完整的错误日志
    ├─ 不要只看最后一行错误
    ├─ 向上滚动，找到第一个 ERROR 或 FAILED
    └─ 理解完整的错误上下文

第三步：识别错误类型
    ├─ 文件缺失类：missing file, No such file → 检查文件是否存在
    ├─ 依赖问题类：cannot find package → 检查依赖声明和实际安装
    ├─ 配置错误类：invalid configuration → 检查配置文件格式
    ├─ 权限问题类：Permission denied → 检查文件权限和 chmod
    └─ 环境问题类：command not found → 检查 CI 环境是否安装工具

第四步：验证假设
    ├─ 提出具体的假设（例如："可能是 gradlew 缺失"）
    ├─ 设计验证方法（例如：在 CI 中运行 ls -la）
    ├─ 执行验证
    └─ 根据结果调整假设

第五步：实施修复
    ├─ 选择最简单的修复方案
    ├─ 提交修复并观察
    └─ 如果失败，回到第三步


【2.3 "推倒重建"的决策标准】

何时应该推倒重建？

✅ 满足以下任意条件时：
    1. 同一个问题修复了 3 次以上仍然失败
    2. 不理解当前配置的来源和含义
    3. 错误信息指向"配置结构本身"有问题
    4. 使用的是网上复制的旧配置
    5. 官方文档的配置与你的完全不同

❌ 不应该推倒重建的情况：
    1. 只是简单的语法错误（拼写、标点）
    2. 错误信息很明确，知道如何修复
    3. 只是某个依赖版本不兼容

如何"推倒重建"？

步骤1：备份当前的业务逻辑代码
    ├─ 提取自己编写的业务代码
    └─ 记录自己做过的配置修改

步骤2：删除所有配置文件和构建文件
    ├─ 例如：删除整个 src-tauri 目录
    └─ 保留业务代码（如 HTML、JS）

步骤3：使用官方 CLI 重新生成
    ├─ 使用最新版本的 CLI
    └─ 使用 --ci 或类似参数生成 CI 友好的配置

步骤4：对比新旧配置
    ├─ 找出差异
    └─ 理解哪些是必须的，哪些是可选的

步骤5：只做必要的修改
    ├─ 修改应用名称、ID 等基本信息
    └─ 添加必要的业务逻辑

步骤4：生成所有密度的图标
----------------------------------------
使用 Python 脚本生成：

import os
from PIL import Image, ImageDraw

densities = {
    'mdpi': 48,
    'hdpi': 72,
    'xhdpi': 96,
    'xxhdpi': 144,
    'xxxhdpi': 192
}

for density, size in densities.items():
    # 创建目录
    dir_path = f'app/src/main/res/mipmap-{density}'
    os.makedirs(dir_path, exist_ok=True)

    # 创建图标
    img = Image.new('RGBA', (size, size), '#0f172a')
    draw = ImageDraw.Draw(img)
    # 添加简单的视觉元素（圆形）
    margin = size // 4
    draw.ellipse([margin, margin, size-margin, size-margin],
                 fill='#38bdf8')

    # 保存两种格式
    img.save(f'{dir_path}/ic_launcher.png')

    # Round 图标（圆形）
    mask = Image.new('L', (size, size), 0)
    draw_mask = ImageDraw.Draw(mask)
    draw_mask.ellipse([0, 0, size, size], fill=255)

    img_round = Image.new('RGBA', (size, size), (0, 0, 0, 0))
    img_round.paste(img, (0, 0))
    img_round.putalpha(mask)
    img_round.save(f'{dir_path}/ic_launcher_round.png')

【3.3 Mac/Windows Tauri 完整配置步骤】

步骤2：创建最小化的 index.html（满足 frontendDist 要求）
----------------------------------------
mkdir -p dist

文件：dist/index.html

<!DOCTYPE html>
<html>
<head>
  <meta charset="UTF-8" />
  <title>Loading MornHub...</title>
  <meta http-equiv="refresh" content="0; url=https://mornhub.help" />
  <style>
    body {
      background-color: #0f172a;
      display: flex;
      justify-content: center;
      align-items: center;
      height: 100vh;
      margin: 0;
      color: white;
      font-family: sans-serif;
    }
  </style>
</head>
<body>
  <p>Redirecting to MornHub...</p>
</body>
</html>

关键理解：
    - Tauri v2 必须要有 index.html，无法绕过
    - 我们不绕过，而是创建一个重定向 HTML
    - 用户体验：应用启动 → 加载 index.html → 立即重定向到远程网站

步骤3：配置 tauri.conf.json（最小修改）
----------------------------------------
文件：src-tauri/tauri.conf.json

{
  "$schema": "../node_modules/@tauri-apps/cli/config.schema.json",
  "productName": "MornHub",
  "version": "1.0.0",
  "identifier": "com.mornhub.desktop",
  "build": {
    "frontendDist": "../dist",  // 指向包含 index.html 的目录
    "devUrl": "https://mornhub.help",
    "beforeDevCommand": "",
    "beforeBuildCommand": ""
  },
  "app": {
    "windows": [{
      "title": "MornHub",
      "url": "https://mornhub.help",  // 这个配置不生效，会被 frontendDist 覆盖
      "width": 1200,
      "height": 800,
      "resizable": true,
      "fullscreen": false
    }],
    "security": {
      "csp": null  // 不要添加 capabilities，除非你知道具体需要什么
    }
  },
  "bundle": {
    "active": true,
    "targets": "all",
    "icon": [
      "icons/32x32.png",
      "icons/128x128.png",
      "icons/128x128@2x.png",
      "icons/icon.icns",
      "icons/icon.ico"
    ]
  }
}

关键点：
    ✅ frontendDist 必须指向包含 index.html 的目录
    ✅ 不要使用 frontendDist: false（不支持）
    ✅ 不要添加不存在的 capabilities
    ✅ 保持配置简单，只改必要的部分

【3.5 GitHub Actions Workflow 配置】

文件：.github/workflows/build-all-platforms.yml

name: 🚀 四端自动构建

on:
  workflow_dispatch:
    inputs:
      platform:
        description: '选择要构建的平台'
        required: true
        default: 'all'
        type: choice
        options:
          - all
          - android
          - mac
          - windows
          - ios
  push:
    branches:
      - main
    paths:
      - 'desktop-apps/**'
      - '.github/workflows/build-all-platforms.yml'

jobs:
  # ===== Android 构建 =====
  build-android:
    name: 📱 构建 Android APK

【4.1 Android 常见错误】

错误0：APK 构建成功但无法安装，提示需要签名
----------------------------------------
现象：下载的 APK 文件无法在 Android 设备上安装
完整错误：应用未安装 / 无法验证应用
根本原因：Release APK 没有签名，Android 系统拒绝安装未签名的应用

解决方案：配置应用签名
步骤1：生成签名密钥库
    keytool -genkey -v -keystore mornhub-release.keystore \
      -alias mornhub \
      -keyalg RSA -keysize 2048 -validity 10000 \
      -storepass "密钥库密码" \
      -keypass "密钥密码" \
      -dname "CN=AppName, OU=Development, O=Company, L=City, ST=State, C=CN" \
      -storetype pkcs12

步骤2：配置 Gradle 签名
    在 app/build.gradle 中添加：
    android {
        signingConfigs {
            release {
                storeFile file(System.getenv("KEYSTORE_FILE") ?: "release.keystore")
                storePassword System.getenv("KEYSTORE_PASSWORD") ?: "默认密码"
                keyAlias System.getenv("KEY_ALIAS") ?: "默认别名"
                keyPassword System.getenv("KEY_PASSWORD") ?: "默认密码"
            }
        }
        buildTypes {
            release {
                signingConfig signingConfigs.release
                minifyEnabled true
                proguardFiles getDefaultProguardFile('proguard-android-optimize.txt')
            }
        }
    }

步骤3：配置 GitHub Actions
    - name: 解码并设置签名密钥
      working-directory: desktop-apps/android-twa
      env:
        KEYSTORE_BASE64: ${{ secrets.ANDROID_KEYSTORE }}
      run: |
        if [ -n "$KEYSTORE_BASE64" ]; then
          echo "$KEYSTORE_BASE64" | base64 -d > release.keystore
        fi

    - name: 构建 Android APK
      env:
        KEYSTORE_FILE: release.keystore
        KEYSTORE_PASSWORD: ${{ secrets.ANDROID_KEYSTORE_PASSWORD }}
        KEY_ALIAS: ${{ secrets.ANDROID_KEY_ALIAS }}
        KEY_PASSWORD: ${{ secrets.ANDROID_KEY_PASSWORD }}
      run: ./gradlew assembleRelease --no-daemon

步骤4：配置 GitHub Secrets
    1. 转换密钥库为 Base64：base64 -i release.keystore | pbcopy
    2. 在 GitHub 仓库 Settings → Secrets → Actions 中添加：
       - ANDROID_KEYSTORE: 密钥库文件的 Base64 编码
       - ANDROID_KEYSTORE_PASSWORD: 密钥库密码
       - ANDROID_KEY_ALIAS: 密钥别名
       - ANDROID_KEY_PASSWORD: 密钥密码

安全注意事项：
    ✅ 密钥库文件必须添加到 .gitignore，不要提交到 Git
    ✅ 密钥库文件只存在于本地和 GitHub Secrets
    ✅ 定期备份密钥库文件（丢失后无法重新生成相同的签名）
    ✅ 生产环境使用强密码

错误1：gradlew: Permission denied
----------------------------------------
原因：gradlew 文件没有执行权限
解决：在 GitHub Actions 中添加 chmod +x gradlew
验证：ls -la gradlew 应该显示 -rwxr-xr-x

错误2：Could not find com.android.tools.build:gradle
----------------------------------------
原因：Gradle 找不到 Android 插件
根源：仓库配置问题
解决：检查 settings.gradle 是否正确配置了 google() 仓库

错误3：Execution failed for task ':app:processReleaseResources'
----------------------------------------
原因：资源文件缺失或引用错误
检查：
    1. AndroidManifest.xml 引用的所有资源是否存在
    2. mipmap 目录是否包含所有密度的图标
    3. strings.xml 是否定义了所有引用的字符串

错误4：FAILURE: Build failed with an exception (仓库冲突)
----------------------------------------
完整错误信息：
    Build was configured to prefer settings repositories over project
    repositories but repository 'Google' was added by build file 'build.gradle'

原因：Gradle 7+ 使用 FAIL_ON_PROJECT_REPOS 模式
解决：
    1. 删除所有 build.gradle 中的 repositories 块
    2. 只在 settings.gradle 中定义仓库


【4.2 Tauri 常见错误】

错误0：Mac 应用无法打开，提示"这台Mac不支持此应用程序"
----------------------------------------
现象：下载的 DMG 安装后无法打开
完整错误：你无法打开应用程序"MornHub"，因为这台Mac不支持此应用程序。
根本原因：CPU 架构不匹配或单架构构建的兼容性问题

【问题详情】
    - macos-latest 运行器默认是 ARM64 (Apple Silicon)
    - 单独构建的 aarch64 版本可能在某些 Apple Silicon Mac 上无法打开
    - 单独构建的 x86_64 版本无法在 Apple Silicon Mac 上运行

【解决方案对比】

方案1：构建 Universal Binary（推荐）⭐
----------------------------------------
优势：
    ✅ 一个安装包同时支持 Intel 和 Apple Silicon
    ✅ 用户无需选择，自动适配
    ✅ 兼容性最好，避免单架构构建的潜在问题
    ✅ 符合 Apple 官方最佳实践

配置示例：
    - name: 添加 Rust 目标 (Intel + Apple Silicon)
      run: |
        rustup target add x86_64-apple-darwin
        rustup target add aarch64-apple-darwin

    - name: 构建 Mac Universal Binary
      run: cargo tauri build --target universal-apple-darwin

    - name: 上传 DMG (Universal)
      uses: actions/upload-artifact@v4
      with:
        name: SiteHub-Mac-Universal
        path: target/universal-apple-darwin/release/bundle/dmg/*.dmg

方案2：使用 matrix strategy 分别构建两种架构
----------------------------------------
缺点：
    ⚠️  需要用户手动选择正确的版本
    ⚠️  单架构构建可能存在兼容性问题
    ⚠️  维护两个构建产物

配置示例：
    strategy:
      matrix:
        target:
          - x86_64-apple-darwin    # Intel
          - aarch64-apple-darwin   # Apple Silicon

用户下载指南（方案2）：
    - Intel Mac (2020年前) → 下载 x86_64-apple-darwin 版本
    - Apple Silicon Mac (M1/M2/M3) → 下载 aarch64-apple-darwin 版本
    - 查看芯片类型：苹果菜单 → 关于本机 → 芯片

【实际遇到的问题】
在测试中发现：
    ✅ Intel Mac + x86_64 单独构建 = 正常工作
    ❌ Apple Silicon Mac + aarch64 单独构建 = 无法打开

原因推测：
    - 单架构构建可能缺少某些系统兼容性处理
    - Universal Binary 由 Apple 工具链正确处理架构融合
    - Tauri 对 Universal Binary 的支持更成熟

【最佳实践推荐】
✅ 优先使用 universal-apple-darwin 目标
✅ 提供单一安装包，用户体验最好
✅ 避免用户因选错版本而无法使用

错误1：error: failed to resolve: could not find 'tauri_plugin_log'
----------------------------------------
原因：Cargo.toml 删除了依赖，但代码还在使用
解决：
    1. 全局搜索 tauri_plugin_log
    2. 删除 src/lib.rs 中所有使用该插件的代码
    3. 或者重新添加依赖到 Cargo.toml

错误2：proc macro panicked: capability with identifier shell-open not found
----------------------------------------
原因：Tauri v2 不支持这个 capability 名称
解决：删除 tauri.conf.json 中的 capabilities 数组
正确做法：
    {
      "security": {
        "csp": null
      }
    }

错误3：frontendDist validation failed
----------------------------------------
原因：Tauri 必须要有有效的 index.html
错误做法：
    ❌ "frontendDist": false
    ❌ "frontendDist": "非existent/path"
    ❌ 删除 build 对象
正确做法：
    ✅ 创建 dist/index.html
    ✅ "frontendDist": "../dist"

错误4：tauri-plugin-log version "2" is not valid SemVer
----------------------------------------
原因：版本号格式错误
错误：version = "2"
正确：version = "2.0.0"
更好：删除这个依赖（如果不需要日志功能）

【4.4 CI/CD 通用错误】

错误0：Unrecognized named-value: 'secrets'（GitHub Actions 严重错误）
----------------------------------------
现象：Workflow 文件验证失败，无法运行
完整错误信息：
    Invalid workflow file: .github/workflows/xxx.yml
    Line XX, Col XX: Unrecognized named-value: 'secrets'.
    Located at position 1 within expression: secrets.XXX != ''

根本原因：GitHub Actions 不允许在 if 条件表达式中直接使用 secrets 上下文

错误示例：
    ❌ 错误写法：
    - name: 某个步骤
      if: ${{ secrets.APPLE_CERTIFICATE != '' }}  # 错误！
      run: echo "执行某些操作"

为什么会出错：
    - secrets 只能在 env 环境变量中使用
    - 不能在 if 条件、表达式、或其他上下文中使用
    - 这是 GitHub Actions 的安全限制

正确解决方案：

方案1：使用 continue-on-error + 在 shell 中检查环境变量
    ✅ 正确写法：
    - name: 某个步骤
      continue-on-error: true  # 允许失败
      env:
        MY_SECRET: ${{ secrets.APPLE_CERTIFICATE }}  # secrets 只能在 env 中使用
      run: |
        if [ -z "$MY_SECRET" ]; then
          echo "⚠️  未配置密钥，跳过此步骤"
          exit 1
        fi
        # 执行实际操作
        echo "使用密钥执行操作"

方案2：将步骤拆分到独立的 job，使用 job 级别的 if
    ✅ 可以在 job 级别使用有限的条件：
    job-name:
      if: github.event_name == 'push'  # 可以使用 github 上下文
      # 但仍然不能使用 secrets

实际案例（iOS 构建）：
    错误代码：
    - name: 导入 Apple 证书
      if: ${{ secrets.APPLE_CERTIFICATE != '' }}  # ❌ 错误！
      env:
        APPLE_CERTIFICATE: ${{ secrets.APPLE_CERTIFICATE }}

    正确代码：
    - name: 导入 Apple 证书
      continue-on-error: true  # ✅ 正确
      env:
        APPLE_CERTIFICATE: ${{ secrets.APPLE_CERTIFICATE }}
      run: |
        if [ -z "$APPLE_CERTIFICATE" ]; then
          echo "⚠️  未配置 APPLE_CERTIFICATE，跳过证书导入"
          exit 1
        fi
        # 实际的证书导入逻辑
        echo "$APPLE_CERTIFICATE" | base64 -d > cert.p12

关键点总结：
    1. ❌ if 条件中不能用 secrets
    2. ✅ env 中可以用 secrets
    3. ✅ 在 shell 脚本中检查环境变量（if [ -z "$VAR" ]）
    4. ✅ 使用 continue-on-error: true 让步骤失败不影响整体
    5. ✅ 提供友好的错误提示

这个错误会导致：
    - Workflow 文件验证失败
    - 所有构建都无法运行
    - 显示红色错误标记
    - 必须修复才能继续

错误1：fatal: pathspec 'xxx' did not match any files
----------------------------------------
原因：试图 git add 一个不存在的路径
解决：
    1. 检查当前目录 pwd
    2. 检查文件是否存在 ls -la
    3. 使用正确的相对路径或绝对路径

错误2：Process completed with exit code 1
----------------------------------------
原因：这是通用的失败退出码
关键：不要只看这一行，向上滚动找真正的错误
方法：
    1. 在 GitHub Actions 日志中展开失败的步骤
    2. 找到第一个 "ERROR" 或 "FAILED"
    3. 阅读完整的错误上下文

错误3：Artifacts 上传失败或找不到文件
----------------------------------------
原因：构建产物路径不正确
解决：
    1. 在构建后添加 ls -R 列出所有文件
    2. 找到实际的产物路径
    3. 修改 upload-artifact 的 path 参数

错误4：Job 被跳过 (skipped)
----------------------------------------
原因：if 条件不满足
检查：
    1. workflow_dispatch inputs 是否正确
    2. github.event_name 是否匹配
    3. 依赖的 job 是否失败（使用 needs）

□ npx cap add ios 已执行
□ dist/index.html 文件存在
□ ios/App/ExportOptions.plist 已创建
□ （如需构建）GitHub Secrets 已配置

GitHub Actions：
□ .github/workflows/*.yml 语法正确
□ 所有 working-directory 路径正确
□ artifact 的 path 指向正确的输出路径
□ （如需 iOS）secrets.APPLE_CERTIFICATE 等已配置


【5.3 构建失败时检查清单】

□ 第一步：确认错误类型
  □ 文件缺失？
  □ 依赖问题？
  □ 配置错误？
  □ 环境问题？

□ 第二步：本地复现
  □ 能否在本地复现？
  □ 本地成功但 CI 失败？

□ 第三步：查看完整日志
  □ 找到第一个 ERROR
  □ 阅读 5-10 行上下文
  □ 理解错误的根本原因

□ 第四步：验证假设
  □ 提出明确的假设
  □ 设计验证方法
  □ 执行并观察结果

□ 第五步：决策
  □ 简单错误 → 直接修复
  □ 复杂错误 → 搜索文档和 Issues
  □ 反复失败 → 考虑推倒重建


【5.4 推倒重建决策清单】

满足以下条件时，应该推倒重建：

□ 同一问题修复 3 次以上仍失败
□ 不理解当前配置的来源
□ 错误指向配置结构本身
□ 使用了网上复制的旧配置
□ 官方文档与当前配置完全不同

推倒重建步骤：

□ 1. 备份业务代码
□ 2. 删除所有配置文件
□ 3. 使用官方 CLI 重新生成
□ 4. 对比新旧配置，理解差异
□ 5. 只做最小化必要修改


【5.5 提交前最终检查】

□ 所有文件已 git add
□ commit message 清晰描述变更
□ 没有提交敏感信息（证书、密码）
□ 本地构建测试通过
□ 准备观察 GitHub Actions 构建结果


================================================================================
                            总结与核心原则
================================================================================

【核心原则1：使用官方工具，不要手动猜测】
    ✅ 使用 CLI 生成标准项目
    ✅ 最小化修改
    ❌ 手动编写复杂配置
    ❌ 复制粘贴旧配置

【核心原则2：理解框架要求，不要试图绕过】
    ✅ 满足框架的基本要求
    ✅ 用巧妙的方法实现目标（如 meta refresh）
    ❌ 试图绕过验证
    ❌ 使用 hack 方法

【核心原则3：失败 3 次，考虑推倒重建】
    ✅ 及时止损
    ✅ 从官方模板重新开始
    ❌ 无限修补
    ❌ 盲目坚持错误方向

【核心原则4：修改依赖时，全局搜索使用位置】
    ✅ 删除依赖前先搜索
    ✅ 同时修改声明和使用
    ❌ 只改 Cargo.toml 不改代码
    ❌ 假设没有其他地方使用

【核心原则5：错误要理解根源，不被表面误导】
    ✅ "chmod error" → 文件缺失
    ✅ "frontendDist validation" → 必须有 index.html
    ❌ 只看最后一行错误
    ❌ 修改表面问题而不解决根源

                          给 AI 助手的建议
================================================================================

如果你是一个 AI 助手，正在帮助用户实现类似的多平台构建，请遵循：

1. 优先使用官方 CLI 工具
   - 不要试图手动创建配置文件
   - 使用 --ci 或类似参数生成 CI 友好的配置

   - 确保声明和使用同步修改

4. 解释错误的根本原因，不只是修复
   - 帮助用户理解"为什么"
   - 提炼规律，避免重复犯错

5. 提供完整的验证步骤
   - 不要只给代码，还要给验证方法
   - 帮助用户建立正确的开发流程
